# Интеграционное и API-тестирование Restful-Booker

**Исходный файл:** `TestingPS/Laba-2.md` (в тексте — работа №3).
**Выполнил:** Мороз Роман, ПВ-233. **Дата прогона:** 26.11.2026.

## Цель, объект и состав работы

Проверить REST API бронирования, автоматизировать передачу token/bookingId,
разделить документированный контракт и ожидаемую бизнес-валидацию.
Объект — [Restful-Booker](https://restful-booker.herokuapp.com/apidoc/index.html).
Публичный сервис учебный и разделяется с другими пользователями.

| Метод и ресурс | Назначение | Кейс |
|---|---|---|
| POST `/auth` | Получить token; неверные credentials | API-01—03 |
| GET `/booking` | Список с фильтром по уникальному имени | API-05 |
| GET `/booking/{id}` | Чтение, отсутствие, контроль изменений и удаления | API-06/09/13/14/26 |
| POST `/booking` | Создание, негативные и граничные данные | API-04/15—24 |
| PUT `/booking/{id}` | Полная замена, отсутствие token | API-07/10 |
| PATCH `/booking/{id}` | Частичное изменение, неверный token | API-08/11 |
| DELETE `/booking/{id}` | Удаление, отсутствие token, повтор | API-12/25/27 и cleanup |
| GET `/ping` | Доступность сервиса | API-28 |

Экспорт: [LabAPI_Moroz](postman/LabAPI_Moroz.postman_collection.json),
[окружение](postman/local.postman_environment.json).
Коллекция состоит из Auth, Booking, Health, содержит 28 основных кейсов и
9 cleanup-запросов. Во всех 37 запросах минимум три проверки: статус, время
менее 2000 мс и непустой ответ; для CRUD добавлены проверки полей и сохранения.

## Переменные и автономный сценарий

`baseUrl` — адрес сервиса; `token` — token из POST auth; `bookingId` — основная
запись; `probeId` — временная запись отдельного граничного кейса; `runName` —
уникальное имя для фильтра. В экспортированном окружении token и ID пустые.
Token передаётся как `Cookie: token={{token}}` только в запросах, где это нужно.
Публичные credentials admin/password123 взяты из задания и не являются секретом.

Начальный auth сбрасывает ID и формирует уникальное имя. Tests сохраняет
token; Tests создания сохраняет bookingid. Дальше без ручного редактирования:
создание → фильтр → чтение → PUT → PATCH → чтение → негативные проверки
авторизации → граничные probes с немедленным cleanup → DELETE → GET 404.
Если probe не создал запись, его cleanup пропускается через `skipRequest`.
Удаляются только ID, полученные от собственных POST текущего прогона.
При аварийном прерывании клиента cleanup не гарантирован — это ограничение
публичного API без общей транзакции.

## Тест-дизайн и фактические результаты

Предусловие: сервис доступен, импортировано окружение; приоритет высокий
для CRUD/авторизации и средний для граничных probes. Шаги и точные payload
хранятся в [cases.json](postman/cases.json); описания цели и ожидаемого
результата есть в каждом запросе. Постусловие: созданные записи удалены.

Полная таблица **ID → endpoint → тип → ожидание → факт → статус** находится
в [api-results.md](evidence/api-results.md), машинный результат —
[api-results.json](evidence/api-results.json).

Реально выполнено **36 запросов, 118 assertions, 7 failed**. Один cleanup
пропущен: API-17 не создал bookingid. Транспортных ошибок не было. Основная
CRUD-цепочка прошла. Шесть FAIL относятся к валидации входов, ещё один —
к времени первого auth: **2692 мс** при локальном бюджете 2000 мс.
Это измерение клиента с сетью и возможным cold start, не серверный SLA.

Классы данных: валидный объект/некорректный JSON/пропущенные поля/неверный
тип; auth валиден/отсутствует/невалиден; ID существует/нет/удалён;
цена 0/−1/2147483647; имена пустые/обычные/1001 символ; даты корректные/
обратный диапазон/невалидный формат. Максимальные длины и денежный лимит
документацией не определены: принятие 1001 символа или большой цены само по
себе не объявляется дефектом.

## Расхождения

Ожидания разделены явно: документированные коды сохраняются в тестах;
`400` для плохих бизнес-данных — тестовая гипотеза о требуемой валидации,
а не дословное обещание документации сервиса.

| № | Запрос | Ожидание и основание | Факт | Вывод |
|---|---|---|---|---|
| 1 | POST auth, неверный пароль | Типичный REST: 401; контракт сервиса: 200 + reason | 200, Bad credentials, token нет | Документированная особенность, PASS |
| 2 | POST booking | REST часто использует 201; контракт сервиса: 200 | 200 + bookingid | Особенность, PASS |
| 3 | DELETE booking | REST обычно 200/204; контракт сервиса: 201 | 201 | Особенность, PASS |
| 4 | GET ping | REST обычно 200; контракт сервиса: 201 | 201 | Особенность, PASS |
| 5 | DELETE уже удалённого ID | Семантически ожидаем 404 | 405 | Особенность реализации, зафиксирована отдельно |
| 6 | API-16 строка в totalprice | Number по схеме; разумное отклонение 400 | 200, totalprice: null | Дефект типовой валидации |
| 7 | API-17 обязательные поля отсутствуют | 4xx для ошибки клиента | 500 Internal Server Error | Дефект обработки ошибочного запроса |
| 8 | API-18 пустые имена | Бизнес-гипотеза: имена обязательны и непусты → 400 | 200, оба имени пустые | Пробел бизнес-валидации, уточнить контракт |
| 9 | API-21 totalprice −1 | Бизнес-гипотеза: цена ≥0 → 400 | 200, −1 сохранено | Пробел бизнес-валидации |
| 10 | API-23 checkout раньше checkin | Бизнес-гипотеза: положительный период → 400 | 200, диапазон сохранён | Пробел бизнес-валидации |
| 11 | API-24 даты not-a-date | Документированный тип Date; отклонение 400 | 200, 0NaN-aN-aN | Дефект проверки/нормализации дат |

## Баг-репорты

Общее окружение: публичный HTTPS API, 26.11.2026, JSON, Accept application/json.
Приоритет P2 — исправить перед реальным использованием; критичность ниже
описывает влияние на систему бронирования, а не учебную ценность сервиса.

| ID | Заголовок / серьёзность | Шаги воспроизведения | Ожидалось | Фактически |
|---|---|---|---|---|
| BUG-API-01 | Неверный тип цены становится null / Major | POST валидного booking, заменить totalprice на not-a-number | 400 с указанием поля, запись не создана | 200, bookingid, totalprice null |
| BUG-API-02 | Пропуск обязательных полей даёт 500 / Major | POST `/booking` с `{firstname: runName}` | 4xx, диагностика отсутствующих полей | 500 Internal Server Error |
| BUG-API-03 | Пустые имена принимаются / Minor, гипотеза | POST валидного booking с firstname и lastname = пустой строке | 400 при обязательном непустом имени | 200, пустые имена |
| BUG-API-04 | Отрицательная цена сохраняется / Major, гипотеза | POST валидного booking с totalprice = −1 | 400 при неотрицательной цене | 200, цена −1 |
| BUG-API-05 | Обратный диапазон дат сохраняется / Major, гипотеза | checkin 2027-01-12, checkout 2027-01-10 | 400 при требовании checkout ≥ checkin | 200, диапазон без исправления |
| BUG-API-06 | Невалидная дата преобразуется в мусор / Major | Обе даты = not-a-date в валидном payload | 400, запись не создана | 200, обе даты 0NaN-aN-aN |

BUG-API-03—05 требуют подтверждения бизнес-контракта владельцем; коллекция
намеренно проверяет строгие ожидания и показывает эти FAIL открыто.

## Запуск и доказательства

```bash
npm ci
npm run test:api
uv run --locked python TestingPS/Laba-2/scripts/api_report.py
```

Команда Newman возвращает **1** из-за найденных расхождений; `--suppress-exit-code`
не применяется. JUnit и подробный JSON создаются в `artifacts/api/`, исходный
JSON может содержать выданный token и не коммитится. Публикуется обезличенная сводка.

В Postman: Import обоих JSON → выбрать окружение → открыть коллекцию → Run
collection → выбрать все папки → Run LabAPI_Moroz. Сохранить скриншот вкладки
Results с числом запросов, assertions и failures. **GUI Collection Runner в
этой среде не запускался**; реальный автоматический прогон выполнен Newman.
Скриншот Newman-отчёта, если приложен, не заменяет скриншот GUI Postman.

## Вывод

Все перечисленные endpoints охвачены; token и ID передаются автоматически,
основная цепочка и cleanup работают без ручной подстановки. Негативные данные
выявили ошибки типовой проверки и обработки входов. Нестандартные HTTP-коды
разделены с дефектами и бизнес-гипотезами. Внешний сервис проверяется отдельным
ручным workflow, чтобы его известные ошибки не определяли готовность локального
магазина к выпуску; сам API workflow сохраняет честный failed статус.
