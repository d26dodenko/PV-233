# Техническое задание: Moroz Store, учебная версия 1.0

**Разработчик:** Мороз Роман, ПВ-233. **Дата:** 26.11.2026.
**Основание:** учебное задание `Specification/Total.md`.
**Статус:** учебное ТЗ для лабораторного контура; реквизиты реального
заказчика, договор и формальное утверждение не подставляются.

Задание просит структуру ГОСТ 34.602-89, но перечисляет восемь учебных
разделов, отличающихся от названий разделов стандарта. Ниже сохранено
содержание задания и выделены сведения об объекте автоматизации и подготовке
к вводу. Это учебная адаптация указанной редакции, не сертификат соответствия.

## 1. Общие сведения: введение и основания разработки

Полное наименование: учебная автоматизированная система интернет-магазина
Moroz Store. Условное обозначение: MS-LAB. Назначение: автоматизировать выбор
товаров, ведение корзины и оформление заказа в контролируемой тестовой среде.

Основание — лабораторное задание по архитектуре и проектированию ППС и
работы по тестированию ПО. Требования учебного заказчика: минимум пять
функций, сравнение трёх архитектур, команда, доска от 20 задач, ТЗ и тесты.
Коммерческие сроки, бюджет и финансирование отсутствуют; этапы и результаты
определены в разделе 5.

## 2. Назначение и цели создания системы

Целевые пользователи: гость, зарегистрированный покупатель, преподаватель.
Автоматизируемые процессы: каталог → поиск → корзина → заказ → история.
Цели: исключить доверие клиентской цене и идентификатору владельца,
обеспечить воспроизводимость проверки и блокировать непроверенный пакет.

Критерии достижения: 10 FR подтверждены таблицей тестов; Python coverage
100%, Rust line coverage ≥80%; тесты и security gates проходят перед упаковкой.
Порог Python строже минимального 80%, заданного в лабораторной.

## 3. Характеристика объекта автоматизации

Учебный магазин содержит три начальных товара, варианты размеров S/M/L/XL,
целочисленные цены в условных USD. Каталог загружается из кода и не меняется
через административную панель. Владелец корзины устанавливается по сессии.
Учётные записи, корзины, заказы и сессии хранятся в памяти одного процесса.
Данные синтетические, денежные операции и отправка сообщений отсутствуют.

## 4. Требования к системе

### 4.1. Структура и функционирование

Слоистый монолит: React-клиент, HTTP Axum, бизнес-правила, Store/Mutex.
Доступ через один origin. Собранный frontend и Rust binary поставляются вместе.
Схемы и сравнение вариантов приведены в [архитектурном отчёте](report.md).

### 4.2. Функции

| ID | Обязательная функция | Критерий приёмки |
|---|---|---|
| FR-01 | Регистрация | Имя 1–100 байт после trim, валидный email, пароль 8–128 байт; 201 или 400 |
| FR-02 | Уникальность email | Trim + lower case; повтор → 409 |
| FR-03 | Авторизация | Правильный пароль → token; неверный → 401; hash Argon2 |
| FR-04 | Просмотр каталога | GET списка → три товара; GET неизвестного → 404 |
| FR-05 | Поиск по названию | Регистр не влияет, отсутствие совпадений показано |
| FR-06 | Добавление | Только покупатель; размер из каталога; quantity 1–99; цена сервера |
| FR-07 | Удаление позиции | Собственная позиция удаляется, чужая недоступна |
| FR-08 | Оформление | Непустая корзина, адрес 5–500 байт после trim; 201, серверная сумма и очистка |
| FR-09 | История | Отображаются только заказы текущего пользователя |
| FR-10 | Выход | Token отозван, повторное обращение с ним → 401 |

Числовой формат цены — целое число условных единиц; дробная цена не
поддерживается. Для реальных денег потребуется отдельная политика minor units
или Decimal. Условия длины backend определены в байтах UTF-8; это отличается
от числа видимых символов и отмечено как ограничение международного UI.

### 4.3. Надёжность и производительность

Внутрипроцессная атомарность заказа и очистки корзины обеспечивается одной
критической секцией; ошибки валидации не создают заказ. При перезапуске
данные сбрасываются — сохранность после рестарта не входит в эту версию.
UI-сценарий обязан завершиться в 30 секунд на лабораторном runner.
Нагрузочные SLA/RPS и доступность 24×7 без измерений не заявляются.

### 4.4. Безопасность

Пароли не сохраняются открытым текстом. Авторизация всех приватных HTTP
маршрутов обязательна, принадлежность данных определяется сервером.
Bearer token случайный, действует не более часа, отзываетcя logout.
Размер JSON тела ограничен 16 КиБ. Цена, userId, totalPrice и статусы
оплаты из клиента не влияют на серверную стоимость или владельца.

Bandit блокирует High; pip-audit и cargo-audit — известные уязвимости;
npm audit блокирует Critical. Уровни High в учебном Newman toolchain
отдельно отражаются в security-отчёте. Лабораторный UI сохраняет bearer
в localStorage по модели upstream; для публичного production контура нужны
HttpOnly/Secure cookie, TLS, rate limiting и постоянное хранилище.

### 4.5. Условия эксплуатации и виды обеспечения

Linux x86_64, Rust 1.100.0, Node.js 24, Python 3.13, Chromium из Playwright
1.56.1. Языки: Rust для backend, TypeScript для UI и Playwright, Python для
pytest и метрик согласно заданиям. Ввод-вывод API — JSON UTF-8.
Зависимости фиксируются lockfiles. API предназначено для loopback-среды,
внешний публичный интерфейс не открывается по умолчанию.

## 6. Порядок контроля и приёмки

1. Выполнить установку из README с lockfiles без их изменения.
2. Запустить pytest: все 67 тестов проходят, строки и ветви — 100%.
3. Запустить cargo tests и cargo-llvm-cov: HTTP-контракт проверен, line coverage ≥80%.
4. Собрать frontend и Rust release binary; запустить шесть E2E.
5. Запустить security gates, проверить ненулевой exit code на учебных fixtures.
6. Запустить Postman/Newman отдельно; известные дефекты публичного API должны
   сохранять FAIL, а цепочка CRUD — выполняться и очищать свои записи.
7. На GitHub запустить обычный CI и gate_demo. При отказе unit/security
   Build должен быть skipped, Required quality gate — failed.
8. Проверить, что для main включён обязательный status check, передать отчёты.

Приёмка локальной части подтверждается файлами evidence. Hosted pipeline,
branch protection и GUI Collection Runner требуют отдельных фактических
доказательств; они не считаются выполненными только из-за наличия YAML.

## 7. Подготовка объекта автоматизации к вводу

Установить инструментальные среды и браузерные библиотеки; выделить
изолированный runner. Доступ к публичному Restful-Booker необходим только
для API-работы и не нужен локальным интеграционным тестам магазина.
Запустить процесс из корня пакета: здесь находится `TestingPS/Laba-3/frontend/dist`.
Не переносить реальные пароли и персональные данные в учебный контур.
Администратор репозитория включает required checks после первого CI-прогона.
