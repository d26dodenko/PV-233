\## Тестируемая система



\*\*Restful-Booker\*\*, открытое учебное API бронирования отелей: https://restful-booker.herokuapp.com (

документация: https://restful-booker.herokuapp.com/apidoc/index.html). Docker и локальный запуск не нужны, достаточно

Postman и доступа в интернет.



| Метод  | Эндпоинт        | Назначение                                             |

|--------|-----------------|--------------------------------------------------------|

| POST   | `/auth`         | получение токена (логин `admin`, пароль `password123`) |

| GET    | `/booking`      | список идентификаторов бронирований (с фильтрами)      |

| GET    | `/booking/{id}` | получение бронирования                                 |

| POST   | `/booking`      | создание бронирования                                  |

| PUT    | `/booking/{id}` | полное обновление (нужна авторизация)                  |

| PATCH  | `/booking/{id}` | частичное обновление (нужна авторизация)               |

| DELETE | `/booking/{id}` | удаление (нужна авторизация)                           |

| GET    | `/ping`         | проверка работоспособности                             |

\## 5. Баг-репорты



\### BUG-01. /auth возвращает 200 OK при неверных или отсутствующих учётных данных

\- \*\*Шаги:\*\* POST `{{baseUrl}}/auth` с телом `{"username":"admin","password":"wrongpassword"}`; повторить с `{}`.

\- \*\*Ожидаемый результат:\*\* 401 Unauthorized, тело с описанием ошибки.

\- \*\*Фактический результат:\*\* 200 OK, `{"reason":"Bad credentials"}` (148–151 мс).

\- \*\*Серьёзность:\*\* Major. Клиент, ориентирующийся на код ответа, считает аутентификацию успешной.



\### BUG-02. Отсутствие обязательных полей при создании бронирования → 500

\- \*\*Шаги:\*\* POST `{{baseUrl}}/booking` с телом `{"firstname":"Bogdan"}`.

\- \*\*Ожидаемый результат:\*\* 400 Bad Request с указанием незаполненных полей.

\- \*\*Фактический результат:\*\* 500 Internal Server Error (147 мс).

\- \*\*Серьёзность:\*\* Major. Ошибка валидации (вина клиента) маскируется под сбой сервера.



\### BUG-03. Пустые (пробельные) строки в обязательных полях принимаются

\- \*\*Шаги:\*\* POST /booking с `firstname:" "`, `lastname:" "`.

\- \*\*Ожидаемый результат:\*\* 400 — обязательные поля не могут быть пустыми.

\- \*\*Фактический результат:\*\* 200 OK, бронирование создано, `firstname:" "` сохранён без обрезки пробелов.

\- \*\*Серьёзность:\*\* Major. В системе появляются брони без имени гостя.



\### BUG-04. Нет валидации типа totalprice: строка принимается и превращается в null

\- \*\*Шаги:\*\* POST /booking с `"totalprice":"сто рублей"`.

\- \*\*Ожидаемый результат:\*\* 400 Bad Request (по документации тип — Number).

\- \*\*Фактический результат:\*\* 200 OK (145 мс), в ответе `totalprice: null` — тихая порча данных.

\- \*\*Серьёзность:\*\* Major.



\### BUG-05. Отсутствует валидация дат (формат и логический порядок)

\- \*\*Шаги:\*\* POST /booking с `checkin:"32-13-2026"`, `checkout:"not-a-date"`; отдельно — checkout (11-15) раньше checkin (11-20).

\- \*\*Ожидаемый результат:\*\* 400 (формат CCYY-MM-DD; checkout ≥ checkin).

\- \*\*Фактический результат:\*\* 200 OK; невалидная дата возвращается как мусорная строка `"0NaN-aN-aN"`; инвертированные даты принимаются.

\- \*\*Серьёзность:\*\* Major. Некорректные брони создаются и отдаются клиентам в повреждённом виде.



\### BUG-06. Отрицательная цена принимается

\- \*\*Шаги:\*\* POST /booking с `totalprice: -100`.

\- \*\*Ожидаемый результат:\*\* 400 Bad Request (цена ≥ 0).

\- \*\*Фактический результат:\*\* 200 OK, бронь с отрицательной стоимостью создана.

\- \*\*Серьёзность:\*\* Major.



\### BUG-07. Успешный DELETE возвращает 201 Created

\- \*\*Шаги:\*\* создать бронирование, получить токен, DELETE `{{baseUrl}}/booking/{{bookingId}}` с `Cookie: token={{token}}`.

\- \*\*Ожидаемый результат:\*\* 204 No Content (или 200 OK).

\- \*\*Фактический результат:\*\* 201 Created, тело «Created».

\- \*\*Серьёзность:\*\* Minor (поведение зафиксировано в документации, но нарушает семантику REST).



\*\*Минорные замечания (без отдельных баг-репортов):\*\* 403 вместо 401 (D-04); 200 вместо 201

при создании (D-02); 201 на /ping (D-11); отсутствие лимитов длины строк (D-12).

Выявлено 12 расхождений с REST/документацией, оформлено 7 баг-репортов. Основные классы

проблем: некорректная семантика кодов ответов (200 при ошибке аутентификации, 500 при

ошибках валидации, 201 при удалении), отсутствие валидации типов, пустых значений, форматов

дат и бизнес-ограничений (отрицательная цена, инвертированные даты). Главный практический

вывод: фактическое поведение API нельзя принимать на веру по документации — необходимы

контрактные проверки кодов и тел ответов, фиксирующие реальные расхождения.
