## 1. Анализ исходного модуля

Объект тестирования: `delivery.calculate_delivery_cost`. Реализация сохраняет
алгоритм из задания; новые ограничения не добавлены.

| Параметр | Назначение | Допустимый класс по смыслу задания | Недопустимый класс |
|---|---|---|---|
| `order_amount: float` | Сумма заказа | Конечное число ≥ 0 | Отрицательное число |
| `distance_km: float` | Расстояние доставки в км | Конечное число ≥ 0 | Отрицательное число |
| `is_premium: bool` | Признак premium | `False`, `True` | Другие типы не оговорены заданием |
| Результат `float` | Стоимость доставки | Неотрицательное число для допустимых входов | Вместо результата при отрицательном входе — `ValueError` |

Аннотации Python не проверяют типы во время выполнения. В тестах используются
как целые, так и дробные числа: оба вида поддерживаются исходной реализацией.
Конечность чисел является предположением предметной области, а не проверкой кода.
Валюта, максимальные значения, точность и округление заданием не определены.

Бизнес-правила и порядок их применения:

1. При `order_amount < 0` выбрасывается `ValueError("order_amount must be >= 0")`.
2. При `distance_km < 0` выбрасывается `ValueError("distance_km must be >= 0")`.
   Проверка суммы выполняется первой: если оба входа отрицательны, ошибка о сумме.
   Бесплатная доставка и premium не отменяют валидацию.
3. При `order_amount >= 5000` стоимость равна `0.0` независимо от допустимого расстояния.
4. При меньшей сумме и `distance_km <= 5` стоимость равна `200.0`.
5. При меньшей сумме и `5 < distance_km <= 20` стоимость равна `500.0`.
6. При меньшей сумме и `distance_km > 20` стоимость равна
   `500.0 + (distance_km - 20) * 30.0`. Дробные километры оплачиваются пропорционально.
7. При `is_premium=True` полученная стоимость умножается на `0.5`;
   нулевая стоимость остаётся нулевой.

Классы эквивалентности суммы: `< 0`, `[0, 5000)`, `[5000, +∞)` для конечных
значений. Расстояния: `< 0`, `[0, 5]`, `(5, 20]`, `(20, +∞)`.
Premium: `False` и `True`; каждый тариф проверяется для обоих классов.

Границы: ноль для обоих числовых входов, 5000 для суммы, 5 и 20 для расстояния.
Проверяются значения до, на и после порогов: `4999.99/5000/5000.01`,
`4.99/5/5.01`, `19.99/20/20.01`, а также `-0.01/0`.
Шаг 0.01 выбран для тест-дизайна и не означает ограничения точности входов.

## 2. Тест-кейсы

Общие атрибуты: предусловие — окружение установлено через `uv sync --locked --dev`,
функция импортирована; приоритет — высокий (расчёт цены и валидация);
шаги — вызвать функцию с тройкой входов из таблицы и сравнить результат
с ожидаемым; для отрицательных входов проверить класс и точный текст исключения.
Постусловие — состояние не изменяется, функция не имеет побочных эффектов.
Автотесты дополнительно проверяют тип результата `float`. Числа сравниваются
с абсолютным допуском `1e-9` и нулевым относительным допуском из-за арифметики float.
Ожидаемые цены заданы явно, без повторения алгоритма функции в тесте.

Входы указаны как `(order_amount, distance_km, is_premium)`.

## 3. Запуск и покрытие

Команды из корня проекта:

```bash
uv sync --locked --dev
uv run --locked pytest -v
uv run --locked pytest -v --cov=delivery --cov-branch --cov-report=term-missing --cov-report=xml --junitxml=test-results.xml
```

Локальный запуск: macOS, Python 3.13.3, pytest 9.1.1, pytest-cov 7.1.0.
Оба запуска успешны: **34 passed**. Покрытие: **15 из 15 исполняемых строк,
12 из 12 исходов ветвления, 100%**, пропущенных строк и частично покрытых
ветвей нет. Протокол второго запуска сохранён в `docs/test-results.txt`.
В этой среде для uv использован локальный кэш (`uv --cache-dir .uv-cache`);
это не меняет зависимости или команду pytest.
CI выполняет последнюю команду на Python 3.11–3.14. Ошибка любого теста,
несогласованный lockfile или покрытие ниже 100% приводят к неуспешному CI.
Локальная проверка и реальный запуск на GitHub — разные проверки:
workflow запускается на GitHub после отправки ветки в репозиторий.

## 4. Оставшиеся риски и вывод

Тесты проверяют все строки и обе стороны каждого условия функции, тарифы,
скидку, бесплатную доставку и порядок валидации. Полное структурное покрытие
не доказывает отсутствие всех дефектов: количество входных значений бесконечно,
а требования могут быть неполными.

Остаются вопросы, которые нужно согласовать до использования в реальном сервисе:

- `NaN` и бесконечность не отклоняются явно. Например, сумма `NaN` не удовлетворяет
  ни проверке отрицательности, ни порогу 5000; расстояние `NaN` может дать цену `NaN`.
- Неверные типы не валидируются единообразно: строки и `None` могут вызвать
  `TypeError`, а любое истинное значение `is_premium`, например строка, даёт скидку.
- Денежные вычисления используют `float`; политика округления до денежных единиц
  и использование `Decimal` не заданы. Допуск в тестах устраняет погрешность сравнения,
  но не решает вопросы денежных расчётов.
- Нет ограничений на очень большие числа, интеграционных проверок источника
  premium-статуса, валюты и фактического расстояния.

Эти вопросы не являются поводом менять готовый алгоритм лабораторной работы
без новых требований. Они фиксируют границы проверенного поведения.

Тестирование связывает требования с наблюдаемым поведением: на этапе анализа
помогает выявить неоднозначности, при разработке проверяет реализацию,
при изменениях обеспечивает регрессионную проверку, перед выпуском даёт
измеримые основания для решения о готовности. В CI проверки выполняются
при каждом изменении, а uv и lockfile обеспечивают повторяемость зависимостей.
Качество ПО также зависит от полноты требований, проектирования и эксплуатации;
автотесты уменьшают риск регрессий, но не заменяют эти части жизненного цикла.
